# ESP32 热敏打印机 · 通用方案设计（草案 v0.1）

> 日期：2026-11-17　硬件：ESP32-WROOM-32E + JX-2R-01（384 点 / 6 段 STB / VH 8.4V）
> 前提：**不再以"接入喵喵机 App"为目标**，协议和固件要能服务多种上位机与多种场景。

---

## 0. 一句话结论

把固件做成 **"点阵优先的双模通用打印机"**：

- 传输：经典蓝牙 SPP 打底（现在就能用），后续按目标场景加 BLE（小程序）或 WiFi（云打印）；
- 协议：**自己的帧协议**（复用已写的 0x02/CRC32 骨架）+ **自动识别 ESC/POS**；
- 排版：**默认上位机排版成 384 点阵**（最灵活、最省 MCU），可选内置字库做文本模式；
- 结构：**接收与打印解耦成两个任务**，否则传输速度会被打印速度拖死（见 §4）。

这样一套固件既能接自家 App/小程序，也能接现成 POS 软件，还能留给以后做云打印。

## 1. 先定产品定位（三条路，只能选一条做主）

| | A. 桌面小票机 | B. 内容/笔记打印机 | C. 云打印节点 |
|---|---|---|---|
| 对标 | 58mm POS 小票机 | 喵喵机/错题打印机 | 飞鹅/易联云 云打印机 |
| 谁排版 | 上位机/POS 软件 | 手机 App / 小程序 | 服务端 |
| 关键能力 | ESC/POS 兼容、快 | 点阵图片、省事 | WiFi + MQTT + OTA |
| 本机短板 | **打印速度（见 §4）** | 无短板 | 需配网/账号/服务端 |
| 变现 | 卖整机给商户 | 卖整机 + 耗材 | 收订阅/流量费 |

**建议**：以 B 为主（本硬件最匹配），A 作为"兼容能力"顺带提供，C 当长期扩展。
理由：MX-2R-01 这类 384 点、6 段串行加热的机器，**天生物理速度上不去**，硬拼小票速度会很难受；而"打图片/文字/二维码/待办/手账/标签"这类内容不要求秒出。

## 2. 现有两条线的复盘

### 2.1 收银方案（POS 小票）
- 现成生态（银豹、客如云、思迅、各类安卓收银机）基本都走 **ESC/POS 指令集 + 经典蓝牙 SPP**；
- 意味着：**只要兼容 ESC/POS 的一个子集，不用改任何 POS 软件就能用**，这是最大的杠杆；
- 但收银小票一般 80–150mm 长，按本机当前速度要 10–25 秒，**顾客会等**。

### 2.2 美团小票方案
- 美团商家版同样有"蓝牙打印机"入口，指令还是 ESC/POS 路线；云打印机则是平台对接（需要厂商资质 + 云端）；
- 一单外卖 15–25cm 长，本机要 20–40 秒 —— 除非做成"后厨 KOT（只打菜品名+桌号，短小票）"或"结账小票（短）"，否则体验不成立；
- 更大的问题是：**平台对接是商务/资质门槛，不是技术门槛**，不适合作为第一个目标。

**结论**：收银/美团不是不能做，而是"本机速度 + 平台门槛"这两条决定了它只能做短小票的补充场景，做不了主力。所以需要新方向。

## 3. 还有哪些新方向（按投入分三档）

### 第一档：几乎零新增能力（只靠点阵 + 现有帧协议）

| 场景 | 说明 | 复用现有代码 |
|---|---|---|
| 排队叫号 / 取号小票 | 号码 + 二维码，10–20 行 | 直接可用 |
| 快递驿站取件码 | 取件码 + 货架号 + 时间 | 直接可用 |
| 停车 / 充电桩小票 | 车牌、时长、金额 | 直接可用 |
| 设备告警小票（IoT） | 温湿度越限、门磁、水浸 → 打一条留痕 | 直接可用 |
| 待办 / 购物清单 / 留言条 | 智能家居（Home Assistant via MQTT）联动 | 直接可用 |
| 抽奖 / 彩票 / 游戏周边 | 随机号码 + 图案 | 直接可用 |
| 学习 / 错题 / 手账 | 拍照 → 点阵 → 打印（对标喵喵机主场） | 直接可用 |

### 第二档：需要文本模式（字库 + 排版 + 条码）

| 场景 | 说明 | 门槛 |
|---|---|---|
| 电子价签 / 资产标签 | 名称 + 条码 + 价格 | ⚠️ **本机只有缺纸光电，没有黑标/间隙定位**，标签会错位，需硬件改 |
| 医疗挂号 / 检验条码 | 姓名 + 条码 + 科室 | 需文本 + Code128/QR |
| 后厨 KOT | 桌号 + 菜品 + 备注（短小票） | 需文本 + 加粗/放大 |
| 门票 / 优惠券 | 券码 + QR + 有效期 | 需文本 + QR |
| 门店交接班 / 日结 | 表格化短小票 | 需文本对齐 |

### 第三档：需要新传输通道或云端（投入大、价值也大）

| 场景 | 说明 | 新增 |
|---|---|---|
| **微信小程序自助打印** | 宿舍/共享/门店扫码打印，用户不装 App | BLE + 小程序蓝牙 API + 服务端 |
| **云打印平台** | 网店订单、外卖聚合、远程打印 | WiFi + 配网 + MQTT + OTA |
| 共享设备小票 | 共享充电宝/寄存柜/洗衣机的凭证 | BLE/WiFi + 设备侧 SDK |
| 有声播报收银 | 收款金额语音播报 | ❌ **本机没焊蜂鸣器/喇叭**，需硬件改 |

**我的建议优先级**：
1. 第一档里挑一个能立刻演示的（推荐 **IoT 告警 / 待办 / 取件码**，做演示最省事）；
2. 第二档的 **文本 + 条码/QR**（这是"打印机价值"的核心，没有它只能打图片）；
3. 第三档的 **小程序 BLE**（真正能规模化的方向，因为用户零安装）。

## 4. 硬件能力边界（决定哪些场景根本不可能）

### 4.1 速度上限（最硬的约束）

一行 = 走纸 + SPI 送数 + 6 段依次加热（6 段必须串行，全部同时加热要 18A，板子给不起）：

| 配置 | 每行耗时 | 等效速度 | 100mm 小票 |
|---|---|---|---|
| 现值：加热 3500µs / 冷却 300µs / 走纸 8ms | 34.2ms | 3.7mm/s | 27s |
| 诊断总结验证值：2000 / 500 | 25.2ms | 5.0mm/s | 20s |
| 调优：1200 / 200 + 走纸 2ms | 13.8ms | 9.1mm/s | 11s |
| 理论地板（加热 800µs×6 + 必要开销） | ~7ms | ~18mm/s | 5.5s |

**结论**：
- 短小票（≤ 40mm）可以接受，长小票（外卖/明细）体验不成立；
- 想再快只有两条路：提高 VH 供电能力（换升压方案，硬件改）或降低加热时间（受纸张和发色阈值限制）；
- 所以 **A 路线（POS 主力机）不现实，B/C 路线（内容/云端）才匹配**。

### 4.2 资源余量

| 资源 | 现状 | 余量 | 影响 |
|---|---|---|---|
| Flash | 1,082,892 / 1,310,720（82.6%） | **仅剩 222KB** | GB2312 一二级字库（6763×32B ≈ **211KB**）**塞不进默认分区**，必须换 `huge_app.csv` 或字库放 LittleFS |
| RAM | 46,236 / 327,680（14.1%） | 281KB | 够开 20KB 接收缓冲 + 双任务；经典 SPP 已占约 60KB |
| 蓝牙 | 经典 SPP 已用 | — | 经典 SPP 与 BLE 可共存但 RAM 紧张，**建议一个固件只开一种**，用编译选项区分 |

### 4.3 传感器限制（容易踩的坑）

- 只有 **1 路缺纸光电**（GPIO35，LM393 数字化），**没有黑标/间隙定位** → 标签纸、连续纸定位都做不了；
- 打印头 NTC（GPIO36）可用，能做**动态浓度补偿**（温度低 → 加长加热时间），这是提升画质最划算的一招；
- 电池采样（GPIO34）已有，但**没有低电保护分级**，打印中掉压会 brownout。

## 5. 协议设计（核心）

### 5.1 分层

```
上位机（App / 小程序 / POS 软件 / 服务端）
   ├── 传输层：经典 SPP（现在） / BLE（小程序） / WiFi-TCP / MQTT（云）
   ├── 会话层：帧协议（自有，0x02…0x03）  ←→  自动识别 ESC/POS 字节流
   └── 应用层：点阵打印 / 文本打印 / 走纸 / 状态 / OTA
```

**自动识别规则**（连上后看首个字节）：
- `0x02` → 进入自有帧模式；
- `0x1B`（ESC）/ `0x40` → 进入 ESC/POS 兼容模式；
- 其他 → 丢弃并等待。

### 5.2 帧层（复用已实现的部分）

```
0x02 | type | seq | len(2,LE) | payload | CRC32(4,LE) | 0x03
```
- CRC32 **用 crcKey `0x35769521` 作初值**（不是标准 zlib 的 0xFFFFFFFF），只覆盖 payload；
- 空载荷帧的 CRC 恒等于 `0x35769521`；
- 真机实测依据：App 的 `SET_CRC_KEY` 帧 payload = `21 95 76 35`（key 的小端），帧内 CRC = `0x2144DF1C`
  = `crc32_seeded(0x35769521, payload)`；书上"ACK 覆盖前 6 字节"的说法实测不成立；
- 分包：单包 payload ≤ 1024（BLE 时 ≤ 200），**每包必回 ACK**，连续 3 包可窗口化（见 §5.5）。

### 5.3 指令集草案（自有，和喵喵机的 47 条无关）

| 码 | 名称 | 方向 | 载荷 | 说明 |
|---|---|---|---|---|
| 0x01 | `PRINT_BITMAP` | ↑ | 高(2) + 48 字节×高 | 原样点阵，最通用 |
| 0x02 | `PRINT_BITMAP_RLE` | ↑ | 高(2) + RLE | BLE/弱链路用 |
| 0x03 | `PRINT_TEXT` | ↑ | 文本(GB2312) + 属性 | 需内置字库 |
| 0x04 | `FEED` | ↑ | mm(1) | 走纸 |
| 0x05 | `SET_DENSITY` | ↑ | 0–100 | 浓度（映射到加热时间） |
| 0x06 | `SET_SPEED` | ↑ | 0–100 | 速度（映射到每步延迟） |
| 0x07 | `PRINT_COMMIT` | ↑ | 空 | 提交任务，开始打印 |
| 0x08 | `ABORT` | ↑ | 空 | 中止当前任务 |
| 0x09 | `GET_INFO` | ↑ | 空 | 回型号/版本/SN/MAC/电量/温度 |
| 0x0A | `GET_STATUS` | ↑ | 空 | 回缺纸/过热/低电/任务状态 |
| 0x0B | `PRINT_TEST_PAGE` | ↑ | 空 | 自检页（M4 用） |
| 0x0C | `ENTER_ESCPOS` | ↑ | 空 | 切到 ESC/POS 模式 |
| 0x0D | `OTA_BEGIN/DATA/END` | ↑ | 分片 | 可选，M4 |
| 0x80 | `STATUS_EVENT` | ↓ | 状态位 + 时间 | **设备主动上报**（见 §5.4） |
| 0x81 | `PRINT_DONE` | ↓ | 行数/耗时/错误码 | 打印结束通知 |

> 设计原则：**上位机掌握排版，打印机只掌握"行"**。这样中英文、条码、logo、表格全在上位机做，固件永远不用改。

### 5.4 状态上报（当前缺失）

现在只有"上位机问 → 设备答"，打印到一半缺纸没人知道。补一条**设备主动推送**：
- 事件：缺纸 / 打印头过温 / 电池低 / 任务完成 / 打印中止；
- 帧类型 `0x80`，无需 ACK（重复推送三次，上位机去重）；
- 这是"能当产品用"的分水岭：收银员必须知道为什么不出纸。

### 5.5 流控（决定会不会丢数据）

- 接收缓冲 **20KB**（≈416 行 ≈ 52mm），够一页小票；
- 发送侧用 `write()` 返回值 + `hasClient()` 重试 —— **不要用 `availableForWrite()`**，这版 `BluetoothSerial` 没实现，永远返回 0（会死循环，已在代码注释里标注）；
- 打印速度 < 传输速度时，**缓冲满了要回"忙"帧让上位机等**，而不是丢包；
- 经典 SPP 的 `RX_QUEUE_SIZE` 默认 512，需改成 20480（改 framework 库文件，或用自己的接收任务读取）。

### 5.6 文本/字体策略（决定 Flash 与体验）

| 方案 | 优点 | 代价 |
|---|---|---|
| A. 上位机排版成点阵（默认） | 零字库、中文/emoji/条码随便、固件不变 | 上位机要图像库；链路要传位图（RLE 可压到 1/5） |
| B. 内置 16×16 GB2312 字库 | 传几百字节就能打一屏字；省流量 | 字库 ≈211KB，需换分区；行宽 24 汉字 |
| C. B + 8×16 ASCII + 条码生成 | 可做"文本 ESC/POS 子集"接 POS | 再多 20–40KB，工作量最大 |

**建议**：A 先做（M1 就能演示）；B 作为 M2；C 只在确定要接 POS 生态时做。

### 5.7 与喵喵机协议的关系

- 已有代码（`frame.cpp` / `crc32.cpp`）**原样保留**，帧格式和 CRC 直接为我所用；
- 喵喵机指令表（`proto.h` 的 47 条）**降级为"兼容插件"**：默认不启用，将来真要做公版 App 兼容时再挂；
- 这样之前写的代码没有浪费，也不会被一份逆向协议绑死。

## 6. 软件架构（必须改的地方）

现在 `loop()` 里同步阻塞打印，**打印 34ms 期间蓝牙的数据会积压甚至丢**。改成双任务：

```
BT 接收任务（优先级 3）        打印任务（优先级 2）
  收字节 → 拆帧 → 校验          取一帧 → 走纸 → SPI → 6 段加热
  → 写环形缓冲 → 回 ACK         → 推进读指针 → 完成时推送 PRINT_DONE
```

- 缓冲：`RingBuffer<20KB>`，读写指针 + 临界区（`portMUX`）；
- 打印任务每行 `vTaskDelay(1)` 让出，喂 WDT；
- 浓度补偿：读 NTC → 查表调加热时间（温度低加长，温度高缩短）；
- 低电保护分级：<3.5V 拒新任务、打印中掉压立即中止并推事件。

## 7. 里程碑（每一步都能独立交付价值）

| 阶段 | 内容 | 交付物 | 预估 |
|---|---|---|---|
| **M1** | 自有帧协议 + 双任务 + 状态上报 + 点阵打印 | 任意上位机发位图就能打，缺纸/完成事件可感知 | 2–3 天 |
| **M2** | 内置字库 + 文本/中文 + QR/条码 | 不用上位机排版也能打小票 | 4–6 天 |
| **M3** | ESC/POS 子集（`GS v 0`、对齐、加粗、切纸/走纸） | 现成 POS 软件/美团商家版能直接调用 | 3–5 天 |
| **M4** | 传输扩展：BLE（小程序）或 WiFi（云打印）+ OTA | 场景真正打开 | 5–10 天 |
| **M5** | 可靠性：低电分级、自动关机、断连重连、自检页 | 可量产 | 3–5 天 |

**M1 就是当前代码的下一个自然台阶**：把"喵喵机指令 dispatcher"换成"自有指令 dispatcher"，其余不变。

## 8. 待你拍板的三件事

1. **主打场景**：IoT/待办/学情（B 路线）还是硬啃收银（A 路线）？→ 决定 M3 优先级。
2. **要不要文本模式**：要 → 换 `huge_app.csv` 分区并做字库；不要 → 永远靠上位机排版。
3. **传输扩展顺序**：BLE（小程序，用户零安装）优先，还是 WiFi（云打印，能做服务端生意）优先？
