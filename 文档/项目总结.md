# ESP32 蓝牙热敏打印机 · 项目总结

> 硬件：ESP32-WROOM-32E + JX-2R-01 机芯（厦门精芯）

## 二、硬件

### 2.1 电源树

```
USB 5V ──TP4056──> 18650 电池 ──软开关(CES806G + AO3401A)──> VBAT_OUT
                                                            ├──> LDO 3V3 ──> ESP32 / 逻辑
                                                            └──> 打印头电源开关(AO3401A+A) ──> VCC_IN
                                                                        └── AP2005 升压 ──> VH(≈8.4V) ──> 打印头
```

- **软开关**：按键 + CES806G 锁存，长按开机/关机；关机时 VBAT_OUT 断开；
- **打印头电源开关**：GPIO17 `VH_EN` 控制，**不打印必须关**（规格书 §3.8 硬性要求）；
- **升压**：AP2005SPER，4.7µH 电感 + SS54 肖特基，反馈分压 R34 33k / R33 11k；
- **输出电容只有 C38 47µF + C39 100nF** —— 这是整机最关键的短板（见 §5.2）。

### 2.3 打印头内部结构（规格书 §3 + 图 2/表 8）

- **384 个发热点**，内部是 **SHIFT REGISTER + LATCH REGISTER + 6 组驱动器（DRIVER）**；
- 每 64 点共用一个 STB，**6 段 × 64 = 384**：

| STB | 覆盖点 | 段内点数 |
|---|---|---|
| STB1 | 1 ~ 64 | 64 |
| STB2 | 65 ~ 128 | 64 |
| STB3 | 129 ~ 192 | 64 |
| STB4 | 193 ~ 256 | 64 |
| STB5 | 257 ~ 320 | 64 |
| STB6 | 321 ~ 384 | 64 |

- **数据方向**：DI 打入的第 1 bit 对应**第 1 号点（最右）**，第 384 bit 对应最左；
  纸向上走，所以**行顺序 = 图像从上到下**；
- 打印头里还集成 **NTC 热敏电阻**（30kΩ @25℃，B=3950）接在 TM 脚；
- 还有一个**反射式光电传感器**（PHK/PHE/VSE）用于缺纸与纸张定位。

**FPC 30 脚定义（规格书 表14，按图纸方向）**

| 脚 | 信号 | 脚 | 信号 |
|---|---|---|---|
| 1 | PHK（光电阴极） | 16 | TM（NTC） |
| 2 | VSE（光电电源） | 17 | TM（NTC） |
| 3 | PHE（光电发射极） | 18 | STB3 |
| 4, 5 | N.C | 19 | STB2 |
| 6, 7 | VH | 20 | STB1 |
| 8 | DI（数据） | 21, 22 | GND |
| 9 | CLK（时钟） | 23 | LAT（锁存） |
| 10, 11 | GND | 24 | DO（级联输出） |
| 12 | STB6 | 25, 26 | VH |
| 13 | STB5 | 27 | MT/A⁻ |
| 14 | STB4 | 28 | MT/A |
| 15 | Vdd（逻辑电源） | 29 | MT/B⁻ |
| | | 30 | MT/B |

> 电机四相也走同一根 FPC —— 所以"打印头排线"和"电机线"是在一起的。

### 2.6 传感器

**缺纸（LM393 比较器）**
- 打印头内的反射式光电：**有纸 → 反射 → 输出低电平；缺纸 → 输出高电平**（规格书 §5.1）；
- 经 LM393（R31 560Ω / R32 10k / R34 10k / R35 15k 分压定阈值）整形成数字量 PHINT；
- 输出开漏 → 需要上拉（板上 R30 10k）；
- 程序中 `digitalRead(PHINT) == HIGH` 即缺纸；
- **规格书明确：缺纸时不要加热；缺纸/自动进纸时必须降速（400~600 PPS）**。

**打印头温度（NTC）**
- NTC 接 TM 脚，板上 10kΩ 上拉到 3V3，NTC 另一端接地；
- 规格书：R25 = 30kΩ ±5%，B = 3950K ±2%，量程 −20 ~ 80℃；
- 公式（B 值法）：
  `1/T = 1/T25 + (1/B)·ln(Rntc/R25)`
- 代码里先算阻值再换算温度：
  `Rntc = R_pullup × Vadc / (Vcc − Vadc)`（本板 R_pullup = 10k，Vcc = 3300mV）
- 硬件实测点：25℃ → 引脚电压 ≈ **2475 mV**（30k/40k × 3.3V），可用来验证标定。

**电池电压**
- 分压 R27 10k / R29 10k（比例 1:1）→ POWER_ADC(GPIO34)，C35 100nF 滤波；
- 用 `analogReadMilliVolts()` 拿校准后的 mV，再 **×2** 还原电池电压；
- 电量百分比用查表（`batVoltagelist[101]`，3.40V 起，4.20V 满），
  因为锂电池放电曲线高度非线性，线性换算会错得离谱。

**主循环（当前）**


## 四、打印时序（一行怎么打出来）

```
① motor_run(4, false, 2000)      走 4 个半步 = 0.125mm      ≈ 8 ms
② delay(2)                       让出 CPU，喂 task WDT       2 ms
③ printhead_send(row)            SPI 48 字节 @1MHz          0.384 ms
④ delayMicroseconds(1000)        数据建立                    1 ms
⑤ for i in 0..5:                 6 段依次加热
     STB_i = 1; delay(heat_us); STB_i = 0; delay(300µs)     6×(3.5+0.3) ms
```

- **必须分段加热**：384 点同时加热要 ~18A，电池和升压都扛不住；
- **段间冷却 300µs** 是给升压电容回充的时间，太短会导致"打几行后变白"；
- 基础加热时间 = `1500 + 热密度 × 20` µs（热密度 0~100，App 默认发 95）；
- **温度补偿**：打印头 ≥50℃ 起线性缩短，80℃ 时约为原值的 70%
  （热敏纸温度越高越容易发色，不补偿会越打越黑甚至糊片）。

**实测耗时**

| 配置 | 每行 | 等效速度 | 25mm(200行) | 50mm(400行) |
|---|---|---|---|---|
| 当前 3500/300 | 34.2 ms | 3.7 mm/s | 6.8 s | 13.7 s |
| 2000/500（诊断总结验证值） | 25.2 ms | 5.0 mm/s | 5.0 s | 10.1 s |
| 1200/200 + 走纸提速 | 13.8 ms | 9.1 mm/s | 2.8 s | 5.5 s |

## 五、为什么它快不起来（工程本质）

### 5.1 能量账（按规格书公式算）

```
P0 = VH² × Rav / (Rcom·N + Rav + Ric + Rlead)²
Rcom·N = 0.05 × 64 = 3.2 Ω
总电阻 = 3.2 + 176 + 6 + 10 = 195.2 Ω

VH = 7.2V：P0 = 0.2395 W/dot（规格书标 0.24W ✓），单段电流 2.36A（标 2.4A ✓）
VH = 8.4V：P0 = 0.326  W/dot，单段电流 ≈ 2.75A
25℃ 发色所需能量 E0 = 0.13 mJ/dot → VH 8.4V 时理论只需 Ton = 0.4ms
```

也就是说：**按规格书，400µs 就够打黑**；我们用 3500µs，是理论值的 9 倍。
多出来的能量并不是"黑度"，而是被 VH 塌陷"吃掉"了（见下）。

### 5.2 升压撑不住一段加热

```
单段功率 = 64 点 × 0.326W ≈ 20.9 W
18650 侧可用功率 ≈ 3.7V × 2A × 0.85 ≈ 6.3 W
47µF 电容储能 = ½CV² = 1.66 mJ
```

一段 3.5ms 需要 ~73mJ，电容只有 1.66mJ、升压只能补 ~22mJ → **VH 必然下跌**。
这就解释了历史问题"打几毫米后整片变白"：
段间冷却不够 → 电容回不来 → 后面的段电压不够 → 白。

**结论**：这台机器的速度不是软件调出来的，是被"47µF + 6.3W 升压"卡死的。
想快只有三条路：加大 VH 电容（如 220µF）、降 VH 到 7.2V（降峰值电流）、
换更大功率的升压方案——都是硬件改动。

## 六、蓝牙与协议（喵喵机 App）

### 6.1 传输层

- 经典蓝牙 **SPP**（不是 BLE），设备名 `MaoPaperang_Q`；
- 安卓原生支持；Windows 配对后变成 COM 口（要选"传出"那个）；**iPhone 用不了**（iOS 只开放 BLE）；
- **必须打补丁**：`BluetoothSerial` 的 `RX_QUEUE_SIZE` 默认 512 字节，
  而 App 一包 `PRINT_DATA` 是 1930 字节 —— 一帧都装不下，会静默丢包。
  改成 20480，脚本见 `工具/patch_bt_rx_queue.py`（框架升级后要重跑）；
- **不要用 `availableForWrite()`**：这版 `BluetoothSerial` 没实现，基类永远返回 0，会死循环；
- SPP 内存占用约 60KB RAM。

### 6.2 帧格式

```
0x02 | type | idx | lenL | lenH | payload | CRC32(4B,LE) | 0x03
```

### 6.3 CRC32（真机实测，和书里写的不一样）

**书上说**：标准 zlib（初值 0xFFFFFFFF），数据帧只覆盖 payload，ACK 覆盖前 6 字节。

**实测**：

| 帧 | payload | 帧里的 CRC | 结论 |
|---|---|---|---|
| `SET_CRC_KEY`(24) | `21 95 76 35`（key 的小端） | `0x2144DF1C` | = **把 key 0x35769521 当初值**、只覆盖 payload |
| 后续帧（如 25 热密度、握手各步） | 各自 payload | —— | = **标准 zlib**（初值 0xFFFFFFFF） |

**所以 App 内部有两套 CRC 实现**（设置密钥那一帧走厂商原生的带 key 算法，
其余走 Java 标准 `CRC32`）。推论：

- **空载荷帧（GET_VERSION 等）用 key 算法时 CRC 恒等于 `0x35769521`**；
- 固件现在是**多规则容错**：主规则（key+payload）、标准 zlib、覆盖帧头、
  以及"用帧里的 key 自校验"，命中哪条记在 `Frame::crc_rule`；
- 串口出现 `（CRC 规则 1 命中：非主规则，请留意）` = **用的是标准 zlib，属于正常现象**
  （规则 0 = key 初值，1 = 标准 zlib，2/3 = 覆盖帧头，4 = 帧内 key 自校验，5 = 全 0）；
- **ACK 只覆盖那 1 字节 `0x00` 载荷**（不是书上说的前 6 字节），
  厂商 `send_ack` 就是这么算的；
- 校验失败**不回任何帧**，让 App 超时重发；不能"跳一字节重找帧头"，会连锁错位。

当前 GET_VERSION 的正确往返：

```
收：02 04 00 00 00 21 95 76 35 03
回：02 04 00 01 00 00 46 89 5E 9E 03
```

### 6.4 握手 10 连（App 连上后依次发，实测顺序）

| 顺序 | App 发 | 载荷 | 设备回 | 回的内容 |
|---|---|---|---|---|
| 1 | 24 SET_CRC_KEY | `21 95 76 35` | ACK | — |
| 2 | 10 GET_SN | 空 | 11 SENT_SN | `"P1001705253855"` |
| 3 | 66 | 空 | 67 | `"BK3432"` |
| 4 | 127 | 空 | 128 | `"v3.38.19"`（12 字节，后 4 字节 0） |
| 5 | 25 SET_HEAT_DENSITY | 1 字节 | ACK | 实测 App 发 **95** |
| 6 | 48 GET_DEV_NAME | 空 | 49 | `"P1"`（2 字节） |
| 7 | 16 GET_BAT_STATUS | 空 | 17 | 电量 1 字节 |
| 8 | 31 GET_POWER_DOWN_TIME | 空 | 32 | 3600 分钟（2 字节小端） |
| 9 | 4 GET_VERSION | 空 | 5 | `01 00 02`（= 2.0.1） |
| 10 | 44 SET_PAPER_TYPE | 1 字节 | ACK | — |

**应答规则**：查询类回 `SENT_*` 数据帧（本身就是应答）；设置类回 11 字节 ACK。
App 对每条指令都要求有回应，不回应会一直重发到超时。

### 6.5 打印流程

```
25 SET_HEAT_DENSITY ×2     设浓度（App 实测发 95）
26 FEED_LINE               第一次：开始一页（清空缓冲）
0  PRINT_DATA ×N           位图数据，每包 ≤1920 字节（=40 行，48 的整数倍）
26 FEED_LINE               第二次：触发打印 → 走纸 + 加热 + 尾部送纸 5mm
```

固件实现（`printjob.cpp`）：

- 页缓冲**按 8KB 翻倍扩容，上限 64KB**（≈1365 行 ≈170mm），小页不吃满；
- **溢出保护**：扩容失败或超过上限时本页标记作废，触发打印时直接拒绝，不再"假装成功"；
- 基础加热 = `1500 + 热密度×20` µs，再按打印头温度线性补偿（≥50℃ 起，80℃ 为 70%）；
- 打印前依次检查：数据完整 → 有纸 → 电压 ≥3.55V，任一不过直接拒绝；
- 打印中：每行查缺纸、每 8 行查过温、每 32 行复核电压（<3.40V 中止）；
- 打印前先回 ACK 再开打，否则 App 等 6 秒超时重发；
- 结束动作：`motor_run(20*4)` 送纸 + `motor_release()` 断线圈 + `printer_end()` 关 VH + 再走 5mm + **清空本页**；
- 打印结束/中止后**排空链路并复位解析器**，防止上一单残留被当成新指令。

## 七、调试过程中踩过/确认的坑

### 7.1 LAY（LAT）极性：教程说反了

- 教程：`LAT` 低有效（idle HIGH，脉冲 LOW）；
- 本机实测：**idle LOW、脉冲 HIGH 才能加热**；
- 原因：JX-2R-01 的 LAT **同时门控加热通路** —— LAT 为 HIGH 时锁存器透明且加热通路关闭，
  这时 STB 拉多高都不出黑；
- 改回 idle LOW / 脉冲 HIGH 后正常。GPIO12 是 strapping 脚，idle LOW 也不影响启动。

### 7.2 段间冷却时间：隐形参数

- 冷却 20µs → 打几毫米后整片变白（VH 塌陷）；
- 冷却 500µs → 整页正常；
- 当前用 300µs（略保守偏小），若出现"后面变白"优先把它加回 500µs。

### 7.3 行数截断

- 曾写死 `print_page(..., 64, ...)`，而图是 200 行 → 只打 1/3；
- 改用 `sizeof(bitmap_page) / sizeof(bitmap_page[0])`，并加 `papertest() == 0` 保护。

### 7.4 `SPI.begin` 的 `-1` 不是"不用"

- ESP32 Arduino 里 `SPI.begin(clk, -1, mosi, -1)` 的 MISO 会被替换成默认脚（GPIO19 = 电机 B-）；
- 现在显式传 `-1` 但**电机初始化在后面**，顺序上没问题；更稳的做法是显式传一个不用的脚。

### 7.5 蓝牙接收队列 512

见 §6.1。这是"App 说发出去了但纸只出一半"的最常见原因。

### 7.6 CRC 初值

见 §6.3。书里两处说法都不准：初值不是 0xFFFFFFFF，ACK 也不是覆盖 6 字节。

### 7.7 `uint8_t` 截断温度

`test_head_temp()` 早期用 `uint8_t temp = get_head_temperature()`，
NTC 断线返回 −99 会变成 157，误判"过温"。现在用 `float`。

### 7.8 看门狗

- `loop()` 里 `delay(1)`；打印循环里每行有 `delay(2)`，能喂到 task WDT（5 秒超时）；
- 如果将来把打印搬到独立任务，`delay` 要换成 `vTaskDelay`。

### 7.9 `SPI.begin` 的 MISO 传 `-1` 会占电机的脚

Arduino-ESP32 会把空的 MISO 自动填成默认脚：VSPI 的 GPIO19 正是电机 B-。
虽然 `motor_init()` 之后会把它改回输出，但顺序上是隐患。现在显式传 GPIO4（未使用）。

### 7.10 打印结束后的"残留错帧"

打印是同步阻塞的，整页期间 App 的数据积压在接收队列里。打印结束后如果直接继续解析，
队列里上一单的字节可能被当成新指令（最坏情况是重新触发一次打印）。
现在打印结束与中止后统一 `print_drain()`：把队列读空、解析器复位。

### 7.11 页缓冲溢出被静默吞掉

旧代码里 `job_append()` 失败只打一行日志，App 仍然收到 ACK，表现为"App 说成功、纸没出"。
现在溢出会把整页标记作废，触发打印时明确拒绝并报数（`本页数据不完整（曾溢出），拒绝打印`）。

## 十一、故障速查

| 现象 | 可能原因 | 处理 |
|---|---|---|
| App 看不到设备 | 名字被过滤 / 没配对 | 系统蓝牙先配对；必要时把 `BT_NAME` 改成 `MaoPaperang` |
| 连上就断 / 转圈 | ACK 语义不对 | 串口看是否每条指令都有回；试 `PROTO_REPLY_ACK_FOR_QUERY 1` |
| `CRC 错` | 算法变体 | 把"收/算/载荷"三行发出来，可反推规则 |
| App 说打印成功但纸白 | 缺纸却被忽略 / VH 没开 / 冷却太短 | 查 `papertest`、`printer_begin`、冷却时间 |
| 打几毫米后变白 | VH 塌陷 | 冷却 300µs → 500µs；或降 VH；或加大 VH 电容 |
| 只打上半截 | 行数/数据包丢失 | 查 `RX_QUEUE_SIZE` 补丁是否生效 |
| 纸走但不加热 | LAT 极性 | 确认 `printhead_send` 里 HIGH 脉冲、idle LOW |
| 电机丢步 | 步进太快 | `MOTOR_STEP_US` 加大（当前 2000µs/半步） |
| 电量永远 100% 或 0% | 单位错（mV vs V） | 查表前除以 1000 |
| 温度报 157℃ | `uint8_t` 截断 | 用 `float` |
| 打印中卡死/复位 | 看门狗 / 掉压 | 查 `delay` 让出、电池电压 |
